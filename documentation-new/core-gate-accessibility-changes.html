Changes to the Drupal Core Accessibility Gate

This document explains the redraft of the Drupal core accessibility gate. The original page mixed policy requirements, historical notes, examples, and tool recommendations. The revised page defines the gate’s scope, required evidence, review triggers, and outcome.

Summary

The revision keeps the page focused on decisions contributors need to make during a core issue. It updates the target from Web Content Accessibility Guidelines (WCAG) 2.1 to WCAG 2.2, clarifies when Authoring Tool Accessibility Guidelines (ATAG) 2.0 applies, and distinguishes a gate decision from a product conformance claim.

The original body contained approximately 909 words. The revised body contains 985 words, an increase of 8.4 percent. The revised structure replaces repeated advice and historical examples with testable requirements and evidence.

The revision:

  • Defines when the gate applies and when an issue can mark it not applicable.
  • States the current WCAG 2.2 Level AA target.
  • Applies ATAG 2.0 separately to authoring interfaces and generated content.
  • Organizes checks around structure, keyboard access, visual presentation, forms, dynamic content, and authoring.
  • Specifies what testing evidence belongs in an issue.
  • Defines a pass, an acceptable follow-up, and reasons to postpone a change.
  • Retains automated testing as one source of evidence rather than treating it as proof of conformance.

Detailed changes

Changes grouped by original section or topic
Original area Change Reason
Page purpose Added an introduction that identifies the gate’s scope and limits. The original page moved directly into standards and checks. It did not explain what passing the gate means or distinguish a change review from a conformance claim for Drupal or a completed site.
“Conforms to WCAG 2.1 and ATAG 2.0” Replaced the combined conformance statement with separate WCAG 2.2 Level AA and ATAG 2.0 Level AA targets, including an explanation of ATAG Parts A and B. WCAG 2.2 is the current W3C Recommendation. WCAG applies to web content and interfaces. ATAG adds requirements for accessible authoring interfaces and support for producing accessible content. Passing one issue gate is not a full conformance evaluation.
Level AAA Described Level AAA success criteria and advisory techniques as encouraged rather than gate requirements, unless another policy or established pattern requires them. A Level AA policy should not silently turn selected Level AAA outcomes into undefined blockers.
When the gate is needed Replaced scattered “when needed” notes with one applicability section covering interface, markup, styling, JavaScript, forms, authoring, and new patterns. Contributors need a predictable way to decide whether the gate applies before implementation and review.
HTML structure Expanded the check to cover native HTML, accessible names, roles, states, relationships, reading order, language information, and text alternatives. A single automated scan cannot establish that HTML structure meets WCAG. The revised checks identify the outcomes that reviewers need to inspect.
Color contrast Placed contrast within a broader visual-presentation section that also covers non-color cues, zoom, reflow, text spacing, forced colors, dragging alternatives, and target size. Contrast is necessary but does not cover the visual and input requirements affected by modern responsive interfaces or the WCAG 2.2 additions.
Form labels Retained labels and added accessible names, required states, input formats, instructions, errors, and correction guidance. Label association is only one part of an accessible form workflow.
“Unplug your mouse” Replaced the instruction with explicit keyboard and focus checks. The original shortcut did not cover focus placement, restoration, visible focus, keyboard traps, or expected component behavior. It also assumed that every contributor uses a detachable mouse.
JavaScript accessibility Replaced historical examples with requirements for keyboard behavior, predictable focus, dynamic announcements, and context changes. Linked the current Drupal.announce() API. Examples such as older drag-and-drop tables, vertical tabs, and jQuery interactions do not define a stable gate and may no longer represent current implementations.
Authoring tools Added a specific check for both the authoring interface and its output. ATAG Part A concerns authors with disabilities. Part B concerns accessible generated content and the support authors need to create it. The original page named ATAG but did not turn that distinction into a review step.
Automated checks Removed the fixed list of browser extensions and services. Described how automation contributes evidence and cited Drupal core’s current axe-core Nightwatch practice. Tool lists age quickly. Automated checks find only some deterministic failures and cannot determine conformance. The policy should define the result required, not prescribe a temporary browser extension.
Disabled automated rules Added a requirement that exceptions be narrow, documented, and linked to a follow-up issue. Current Drupal core accessibility tests use targeted rule exceptions with issue references. Broad suppression can hide regressions.
Issue evidence Added a repeatable evidence checklist covering tasks, steps, states, themes, viewports, automated results, manual checks, assistive technology, and limitations. The original page recommended before-and-after checks but did not say what a reviewer needs in order to reproduce or evaluate them.
Existing patterns Retained the preference for established patterns, with the qualification that the pattern must fit the task and have no relevant known accessibility problem. Reusing a pattern reduces unnecessary variation, but precedent does not prove accessibility.
needs accessibility review Kept the issue tag and added concrete triggers for applying it early. The original page associated the tag mainly with new patterns and jQuery. Complex interactions and unresolved cross-disability effects also warrant review.
Gate decision Added explicit pass, follow-up, and postpone conditions. A gate that lists practices without a decision rule cannot be applied consistently.

Content removed or consolidated

  • Drupal 8 gate discussion: Removed from the main guidance because it is historical context rather than a current requirement.
  • WCAG 2.0 links under WCAG 2.1 headings: Replaced with the WCAG 2.2 Recommendation.
  • Repeated “When needed,” “Details,” and “Resources” blocks: Consolidated into applicability, required checks, evidence, and related guidance.
  • WAVE, Functional Accessibility Evaluator, Accessibility Developer Tools, and Tanaguru tool list: Removed as a fixed policy list. Contributors may use suitable tools, while the gate specifies the evidence required.
  • Old contrast issue and browser-extension links: Removed because they do not define the current requirement.
  • Drupal 6 history for #title and #title_display: Removed because current form behavior belongs in coding standards and API documentation, not in the gate policy.
  • jQuery-specific “problem pattern” language: Replaced with implementation-independent review triggers.
  • Historical JavaScript examples: Replaced with required interaction outcomes and a current core API reference.

Claims not added

The revision does not claim that:

  • Passing the issue gate establishes WCAG or ATAG conformance for Drupal core, a feature, or a completed site.
  • An automated checker can find every accessibility barrier.
  • Every change needs testing with every browser and assistive-technology combination.
  • Every user-interface change requires approval from an accessibility maintainer.
  • Level AAA success criteria are blockers under a Level AA policy.
  • A legal accessibility obligation can be determined from this engineering gate.
