Accessibility is part of contribution quality. Consider it when planning, designing, implementing, reviewing, and testing changes to Drupal core, contributed modules, themes, and distributions.

Start early. Accessibility problems are usually easier to prevent than to correct after an interface and its technical approach are established.

Make accessibility a shared responsibility

Everyone contributing to a change has a role in accessibility. Designers should consider different ways people perceive and operate the interface. Developers should use accessible patterns and add appropriate tests. Reviewers should examine user impact and test evidence. Maintainers should not approve a known regression.

A project may name an accessibility lead or champion to coordinate this work, track questions, and arrange reviews. That role does not make one person responsible for finding or resolving every barrier.

Use the relevant standards

Drupal projects should target Web Content Accessibility Guidelines (WCAG) 2.2 Level AA for user interfaces and rendered content. Apply the Authoring Tool Accessibility Guidelines (ATAG) 2.0 to content-authoring functionality. ATAG Part A addresses accessibility for authors with disabilities. Part B addresses support for producing accessible content.

Follow Drupal’s Accessibility Coding Standards. Level AAA success criteria and advisory techniques are useful goals, but they are not Level AA requirements.

Plan before implementation

Describe the affected user task and the people who could encounter barriers. Include disabled people explicitly instead of reporting only the technical failure. Identify the applicable WCAG or ATAG requirements and add accessibility outcomes to the acceptance criteria.

Use an established Drupal pattern when it fits the task and has no known accessibility problem that affects the change. For a new or substantially changed pattern, review the interaction and implementation approach before the design becomes difficult to change.

For authoring features, consider both sides of the workflow: whether disabled authors can use the interface and whether the feature helps every author produce accessible content.

Test during development

Test the completed interface in the states affected by the change. Automated tools are useful for finding some deterministic failures, but they cannot determine WCAG conformance or replace manual testing.

Testing should include, when relevant:

  • Keyboard operation, visible focus, focus order, and focus restoration.
  • Zoom, reflow, text spacing, responsive layouts, and forced-colors mode.
  • Labels, instructions, errors, status messages, and dynamic updates.
  • Screen readers or other assistive technology when the behavior depends on their interpretation.
  • Automated regression coverage for new or substantially changed interactive behavior, where practical.

Test with disabled users for new, complex, or high-impact patterns when possible. Testing by disabled users adds evidence that cannot be reproduced by simulating disability or using assistive technology occasionally. It does not replace standards-based review.

Use the step-by-step guide to performing an accessibility review.

Record evidence in the issue

Provide enough information for another contributor to repeat the test. Record the affected task, test steps, configuration, theme, viewport, relevant interface states, and expected and actual results. Include automated and manual results, assistive-technology combinations used, and any known limitations.

Describe who is affected and how the barrier changes their ability to complete the task. Link related or follow-up issues. Do not move a regression introduced by the contribution into a follow-up issue.

Request accessibility review when needed

Ask for review early when a change introduces a new or substantially revised pattern, creates a complex interaction, affects several disability groups, or leaves an accessibility question unresolved. For Drupal core issues, add the needs accessibility review tag.

Accessibility Topic Maintainers and other experienced contributors can help identify risks and evaluate evidence. Their involvement does not transfer responsibility for the contribution to the reviewer. Routine changes that follow established patterns and provide adequate evidence do not need a formal review at every development stage.

Apply the Drupal core accessibility gate

Changes to Drupal core that affect user interfaces, rendered output, or authoring must meet the accessibility gate. The issue should show that the applicable checks were completed and that the change introduces no unresolved failure of the project’s accessibility requirements.

The core gate does not apply to every contributed project automatically. Contributed projects should document their own review and release requirements while following Drupal’s accessibility standards.

If work is already underway

Start with the current design and implementation. Identify affected tasks, run the relevant checks, document the results, and address regressions before release. Ask for help if the correct outcome or implementation is unclear. A late review may require substantial changes, but delaying the review will not reduce that work.

Get help

Use the project issue queue for decisions that need to remain with the contribution. For broader questions, join the #accessibility channel in Drupal Slack or attend Drupal accessibility office hours.
