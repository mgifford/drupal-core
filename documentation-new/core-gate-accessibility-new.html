The accessibility gate applies to Drupal core changes that affect a user interface, rendered output, or the content-authoring experience. It helps reviewers determine whether a proposed change introduces an accessibility barrier or makes an existing barrier worse.

Passing this gate means that the issue provides enough evidence to evaluate the change and that the change does not introduce an unresolved failure of the applicable requirements. It is not a claim that Drupal core, a feature, or a completed site fully conforms to an accessibility standard.

Standard

Drupal core targets Web Content Accessibility Guidelines (WCAG) 2.2 Level AA. Level AAA success criteria and advisory techniques are encouraged when they improve the experience, but they are not gate requirements unless another core policy or established pattern requires them.

Drupal is also an authoring tool. Drupal core targets Authoring Tool Accessibility Guidelines (ATAG) 2.0 Level AA for applicable authoring functionality. Part A addresses accessibility for authors with disabilities. Part B addresses support for producing accessible content.

An existing accessibility problem does not justify a new regression. Keep the change from increasing the barrier, and document any related problem that is outside the issue’s scope.

When the gate applies

Apply this gate when a change:

  • Adds or changes a public-facing or administration interface.
  • Changes templates, rendered markup, styling, icons, or visual states.
  • Adds JavaScript, Ajax behavior, focus management, or dynamic updates.
  • Changes forms, validation, error messages, instructions, or input requirements.
  • Changes an editor, media tool, layout tool, or other authoring workflow.
  • Adds or substantially changes a user-interface pattern.

Changes with no effect on user-facing output or interaction can record that the gate is not applicable.

Required checks

Test the completed interface, not only its source code or default state. The checks below are required when they are relevant to the change.

Structure and semantics

  • Use native HTML elements when they provide the required semantics and behavior.
  • Provide accessible names and programmatically determinable roles, states, properties, instructions, and relationships.
  • Preserve a logical heading structure, reading order, landmarks, lists, tables, and language information.
  • Provide useful text alternatives for meaningful non-text content and hide decorative content from assistive technology.

Keyboard and focus

  • Make every action available by keyboard without requiring a pointer gesture.
  • Use a logical focus order and a visible focus indicator.
  • Place and restore focus predictably when dialogs, menus, overlays, Ajax updates, or other interface states open and close.
  • Avoid keyboard traps. If focus is intentionally contained, provide the expected way to leave or close the context.

Visual presentation and input

  • Meet the applicable contrast requirements for text, controls, states, and essential graphics.
  • Do not use color, position, shape, sound, or motion as the only way to convey information.
  • Test zoom, text spacing, reflow, responsive layouts, and forced-colors mode when the change can affect them.
  • Provide a non-dragging alternative for drag interactions and sufficient target size where WCAG 2.2 requires it.

Forms and dynamic content

  • Associate every control with a visible label or another appropriate accessible name.
  • Make required states, formats, instructions, errors, and correction guidance available programmatically.
  • Announce meaningful dynamic changes when they are not otherwise apparent. Use Drupal’s Drupal.announce() API where appropriate.
  • Do not unexpectedly change context when a user focuses, enters, or selects a value.

Authoring workflows

When a change creates or modifies content, test both the authoring interface and its output. Avoid automatically generating inaccessible content. Preserve accessible information during editing and transformation, and provide authors with the prompts, checks, repair options, and documentation needed to produce accessible content.

Testing and evidence

Record enough information in the issue for another contributor to repeat the test. Include:

  • The affected user task and the steps used to test it.
  • The relevant theme, viewport, configuration, and interface states.
  • Before-and-after results, or the expected and actual results.
  • Results from an automated accessibility checker, including any relevant rules that were disabled.
  • Manual keyboard results and other relevant checks, such as zoom, reflow, text spacing, forced colors, reduced motion, or touch input.
  • Browser and assistive-technology results when the change depends on their behavior.
  • Known limitations and links to any follow-up issues.

New or substantially changed interactive patterns should include automated regression coverage where practical. Complex or high-impact changes may also need testing with disabled users. Follow Drupal’s guide to performing an accessibility review.

Automated testing

Automated tools can identify some deterministic failures, but they cannot determine WCAG conformance or replace manual testing. Run the checker on relevant pages, viewports, and interaction states. Compare the change with the current behavior and resolve any new failures.

Drupal core uses axe-core in Nightwatch tests on representative pages and states. A rule should be disabled only when the exception is narrow, the reason is documented, and a follow-up issue tracks the underlying problem. Do not use broad rule suppression to make a test pass.

Accessibility review

Use an established core pattern when it fits the task and has no known accessibility problem that affects the change. Add the needs accessibility review issue tag early when a change introduces a new or substantially revised pattern, creates a complex interaction, affects several disability groups, or has unresolved accessibility questions.

An accessibility review is part of the gate evidence. It does not transfer responsibility for accessibility to the reviewer.

Gate outcome

The gate passes when the applicable checks are complete, the evidence is recorded, and the change introduces no unresolved failure of an applicable WCAG 2.2 Level A or AA success criterion or ATAG 2.0 Level A or AA success criterion.

A separate follow-up issue is acceptable for a pre-existing or out-of-scope problem only when the proposed change does not make it worse. Postpone the change when it introduces a regression, omits an accessible way to complete the task, hides relevant test failures, or does not provide enough evidence to review a complex or high-risk interaction.
