Changes to “How to Ensure Your Contribution Is Accessible”

This document explains the redraft of How to Ensure Your Contribution Is Accessible. The original page was last updated on September 22, 2023. It described an accessibility-champion model and a four-stage sign-off process. The revision makes the guidance applicable to ordinary contributions as well as large initiatives and aligns it with the proposed revision of the Drupal core accessibility gate.

Summary

The revised page treats accessibility as a shared contribution responsibility. It retains the option of naming an accessibility lead or champion, but makes that a coordination role rather than the person responsible for accessibility. It replaces mandatory review at design, alpha, beta, and stable stages with risk-based review triggers.

The original body contained approximately 711 words. The revised body contains 768 words, an increase of 8.0 percent. The additional detail defines practical work products, including user impact, acceptance criteria, tests, and issue evidence.

The revision:

  • Updates the standard from WCAG 2.1 to WCAG 2.2 Level AA.
  • Explains ATAG 2.0 Parts A and B in the context of Drupal authoring features.
  • Separates guidance for all Drupal projects from the formal Drupal core gate.
  • Replaces universal maintainer sign-off with review based on the risk and complexity of a change.
  • Requires contributors to describe affected people and tasks, not only technical failures.
  • Adds manual, automated, assistive-technology, and disabled-user testing guidance.
  • Defines the evidence another contributor needs to repeat a test.

Detailed changes

Changes grouped by original section or claim
Original area Change Reason
Introduction Replaced the conversational opening with a direct statement that accessibility is part of contribution quality throughout planning, design, implementation, review, and testing. The original opening described good intentions but did not say what contributors need to do.
BBC Accessibility Champions Removed the external case study as the basis for Drupal’s process. A single organization’s model does not define current Drupal governance. The useful part of the model, naming someone to coordinate accessibility, is retained without making it mandatory.
“Find an A11y Champion” Replaced the section with “Make accessibility a shared responsibility.” An accessibility lead or champion remains optional. Assigning accessibility to one person creates a predictable ownership gap. Designers, developers, reviewers, and maintainers each control different accessibility outcomes.
WCAG 2.1 and ATAG 2.0 essentials Updated the target to WCAG 2.2 Level AA and explained the distinct purpose of ATAG Parts A and B. Added Drupal’s coding standards as the implementation reference. The original standard was outdated and the term “essentials” did not identify a testable target.
Level AAA Added a short statement that Level AAA and advisory techniques are useful goals but are not Level AA requirements. This keeps aspirational improvements visible without misclassifying them as mandatory failures under an AA target.
Accessibility planning Added requirements to identify affected people and tasks, applicable standards, and accessibility acceptance criteria before implementation. The original page recommended early involvement but did not define what an early review should produce.
Existing patterns Added guidance to reuse an established Drupal pattern only when it fits the task and has no relevant known accessibility defect. Consistency helps, but existing code is not proof that a pattern is accessible.
Authoring workflows Added separate consideration of the interface used by disabled authors and the accessibility of generated content. This turns the ATAG reference into a concrete design and review decision.
Design, alpha, beta, and stable reviews Removed the four-stage minimum review schedule and replaced it with continuous testing plus risk-based review triggers. The staged model may fit a large initiative, but it adds unnecessary process to small changes and does not match the core-gates principle that gates should not add work for the responsible team.
Accessibility Topic Maintainer sign-off Removed the claim that every core contribution needs Topic Maintainer sign-off and the recommendation to obtain official sign-off at every stage. The core gate is a checklist for developers, reviewers, and committers. Topic Maintainer review is important for new, complex, high-impact, or unresolved work, but should not be represented as a universal approval step without a supporting governance policy.
Testing Added a concise set of manual, automated, responsive, assistive-technology, regression, and disabled-user testing expectations. The original page said to perform reviews regularly but did not explain the minimum shape of a useful review.
Issue evidence Added requirements for reproducible steps, relevant configurations and states, expected and actual results, affected people, and known limitations. Reviewers need evidence they can repeat. A request for sign-off is not evidence.
needs accessibility review Added the core issue tag and concrete conditions for using it early. The tag connects process guidance to the accessibility gate and makes review needs visible in the issue queue.
Core and contributed projects Clarified that the formal core gate applies to Drupal core. Contributed projects should define their own review and release requirements. The original page grouped core, modules, themes, initiatives, and patches together, then described a core-only approval process as if it applied to all of them.
Work already underway Replaced the question-and-answer section with direct steps for assessing and correcting work in progress. The revised wording tells contributors what to do without reassurance, repetition, or dependence on finding a champion.
Getting help Retained the issue queue and Drupal Slack channel, and added the current accessibility office-hours page. Decisions should remain documented with the contribution. Community channels remain useful for broader questions and early advice.

Content removed or altered

  • “A11y” in the main heading: Replaced with “accessibility.” The abbreviation remains only where it is part of a channel or page name.
  • BBC success claim: Removed because the page did not provide evidence needed to evaluate the claim and Drupal’s process should stand on its own policy.
  • Monthly office-hours promise: Replaced with a link to the maintained office-hours page. The contribution guide should not contain a schedule that can become stale.
  • Mandatory four-stage sign-off: Removed because it is disproportionate for routine contributions and unsupported as a universal policy.
  • “Here to help, not judge” and similar reassurance: Removed in favor of direct instructions and current support routes.
  • Legal-obligation claim: Removed because obligations vary by organization and jurisdiction and do not define Drupal’s engineering process.
  • Claim that late remediation can make a theme “ugly”: Removed as subjective and unnecessary.
  • Claims that accessible work is always easier, cheaper, or more elegant: Replaced with the narrower and defensible point that prevention is usually easier than correcting an established design and implementation.

Claims not added

The revision does not claim that:

  • One accessibility champion can assure the accessibility of a contribution.
  • Every contribution requires Accessibility Topic Maintainer approval.
  • Passing an automated test establishes WCAG conformance.
  • Testing with one screen reader represents all disabled users.
  • Testing with disabled users replaces standards-based review.
  • Every contributed project uses the Drupal core accessibility gate.
  • Following the page establishes legal compliance.
