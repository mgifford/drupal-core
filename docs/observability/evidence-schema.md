# Evidence manifest format

The machine-readable record of one test run:
[`schemas/quality-evidence.schema.json`](../../schemas/quality-evidence.schema.json),
version 0.1.0, JSON Schema 2020-12. The schema is the authority; this page
explains it. For how manifests are made, see [README.md](README.md).

A real example, generated by the evidence runner with server tracing on, is
[`schemas/examples/quality-evidence-run.example.json`](../../schemas/examples/quality-evidence-run.example.json)
(run `run-20261124T134220Z-1ca3d340`, copied unchanged). The artifact files
it lists are private and not included. The workflow
`.github/workflows/evidence-tools.yml` validates it, and runs the unit
tests, on every change to the schemas, the evidence tools or the other
unit-tested scripts.

Validate any manifest or investigation request with:

```bash
node tests/playwright/scripts/evidence.mjs validate <file>...
```

## Structure

| Field | Holds |
| --- | --- |
| `schema_version`, `artifact_type` | `0.1.0` and `quality-evidence-run` |
| `run` | Run id, start and end times, status, trigger (`manual`, `scheduled`, `ci`), mode, and `synthetic` |
| `target` | Product, source repository, ref, commit and dirty flag, Drupal and PHP versions, install profile, recipes, `composer.lock` SHA-256 |
| `environment` | Site origin, browser name and version, viewport, colour scheme, reduced motion, runner |
| `instrumentation` | Whether server tracing was `enabled`, `disabled` or `unknown`, and where this run's raw spans are |
| `tools` | Name and version of each tool used |
| `scenarios` | Each scenario, its attempts, and each attempt's actions, requests and correlation summary |
| `findings` | Scanner results, one per element, with fingerprint, verification and source mapping |
| `measurements` | Numbers with their unit, kind, method and whether tracing was on |
| `artifacts` | Files the run produced, with hash, size, visibility and availability |
| `related_issues` | Optional links to drupal.org, GitHub or Core Lab |

## Identifiers

Every record type has its own id format, so ids cannot be confused:
`run-<UTC time>-<8 hex>`, and `att-`, `act-`, `req-`, `fnd-`, `msr-` and
`art-` followed by 12 hex digits. These are random and local to this
project.

Trace ids (32 hex) and span ids (16 hex) are the only OpenTelemetry ids.
They come from the server's `traceresponse` header and appear only on
requests whose trace status is `correlated`, on attempt correlation
summaries, on findings and on measurements.

## Statuses

- `run.status` and attempt `status`: `PASS`, `FAIL`, `SKIPPED`,
  `INCONCLUSIVE`, `NOT_RUN` or `INFRASTRUCTURE_ERROR`. A run with no
  scenario records is `NOT_RUN`, never `PASS`.
- `run.mode`: `diagnostic` (instrumented, for investigation) or `benchmark`
  (controlled measurement). The two must not be compared.
- Request and attempt trace statuses: see
  [README.md, "Trace correlation"](README.md#trace-correlation).

## Findings

- `result`: axe-core violations become `violation`; axe-core "incomplete"
  results become `needs-review`.
- `rule_id` and `engine_tags` are the engine's own values, unchanged.
- `wcag_candidates` are success criteria read from the engine's tags. They
  are candidates, not a conformance judgement.
- `verification` starts as `automated-unreviewed`. Only a person can set
  `human-confirmed`, `human-rejected` or `disputed`.
- `source_mapping.classification` is `verified`, `probable`, `candidate` or
  `unknown`. The pilot produces only `candidate` (a route from the page
  load's server trace) and `unknown`.
- `fingerprint` identifies the same finding across runs. Its status is
  `provisional` until selector normalization is applied.
- `url` and `html` are sanitized when recorded (see
  [README.md, "Security and privacy"](README.md#security-and-privacy)).

## Measurements

`kind` separates what was measured from what was estimated:
`server-execution`, `browser-timing`, `resource-proxy`, `energy-measured`,
`energy-estimated` and `emissions-modelled`. `instrumented` is true when
server tracing was on; instrumented values are not comparable with
uninstrumented ones. `method` says in words how each value was obtained.

## Artifacts

- `visibility: private` marks files that may hold URLs, statement text,
  stack traces, form tokens or screenshots of the test site. They must not
  be published.
- `availability` is `available`, `expired`, `not-collected` or `withheld`.
  An `available` artifact must have a `path`, `sha256` and `bytes`.
- `path` is relative to the run folder: no leading slash, no `..`, no URL
  scheme.

## Versioning

The `$id` and `schema_version` carry the version. While the major version
is 0, a new version may change fields without a migration. Consumers
should check `schema_version` and refuse versions they do not know.
